## はじめに

AWS Cognito を使用して認証基盤を実装しました。  
そこで学んだことをまとめたいと思います。

### 採用した技術

| カテゴリ           | 技術                     |
| ------------------ | ------------------------ |
| バックエンド       | Spring Boot 3.5, Java 21 |
| 認証基盤           | AWS Cognito              |
| ソーシャルログイン | Google SSO (OAuth 2.0)   |
| トークン形式       | JWT (JSON Web Token)     |
| トークン保存       | HttpOnly Cookie          |
| セキュリティ       | Spring Security          |

## AWS Cognito とは

AWS Cognito は、AWS が提供するユーザー認証・認可サービスです。

### 主な機能

- ユーザー管理  
  ユーザーの登録、ログイン、パスワードリセット
- トークン発行  
  JWT（Access Token, ID Token, Refresh Token）の発行
- ソーシャルログイン  
  Google, Facebook, Apple などとの連携

## なぜ AWS Cognito を選んだか

### 自前実装との比較

| 項目                     | 自前実装               | AWS Cognito                 |
| ------------------------ | ---------------------- | --------------------------- |
| パスワードのハッシュ化   | 自分で実装             | 自動で管理                  |
| トークンの発行・検証     | 自分で実装             | Cognitoが発行、公開鍵で検証 |
| リフレッシュトークン     | 自分で実装             | 組み込み機能                |
| ソーシャルログイン       | 各プロバイダと個別連携 | 設定のみで連携可能          |
| セキュリティアップデート | 自分で対応             | AWSが自動対応               |

このように、AWSでの設定のみで簡単に、そしてセキュアに実装できます。

### Cognito の設定手順

#### Step 1: ユーザープールの作成

AWS コンソールでは「ユーザー名のみ」でユーザープールを作成しようとすると、「メールアドレスまたは電話番号を必須属性として設定する必要があります」という制約があります。これを回避するため **AWS CLI** で作成します。

```bash
# ユーザープールの作成（ユーザー名のみ、メール/電話番号なし）
aws cognito-idp create-user-pool \
  --pool-name "user-pool" \
  --username-attributes "" \
  --auto-verified-attributes "" \
  --username-configuration "CaseSensitive=false" \
  --admin-create-user-config "AllowAdminCreateUserOnly=true" \
  --policies "PasswordPolicy={MinimumLength=8,RequireUppercase=true,RequireLowercase=true,RequireNumbers=true,RequireSymbols=false}" \
  --region ap-northeast-1
```

**オプションの説明:**

| オプション                      | 説明                                      |
| ------------------------------- | ----------------------------------------- |
| `--username-attributes ""`      | メール/電話番号をユーザー名として使わない |
| `--auto-verified-attributes ""` | 自動検証する属性なし                      |
| `--admin-create-user-config`    | 管理者のみがユーザーを作成可能            |
| `--policies`                    | パスワードポリシーの設定                  |

#### Step 2: アプリケーションクライアントの設定

1. 「アプリクライアントを作成」
2. アプリクライアント名：任意の名前
3. **クライアントシークレットを生成しない**（パブリッククライアント）
4. 認証フロー：
   - `ALLOW_USER_PASSWORD_AUTH`（ID/Password 認証用）
   - `ALLOW_REFRESH_TOKEN_AUTH`（トークンリフレッシュ用）

#### Step 3: Google SSO の設定

**Google Cloud Console 側:**

1. Google Cloud Console → 「APIとサービス」→「認証情報」
2. 「認証情報を作成」→「OAuth クライアント ID」
3. アプリケーションの種類：「ウェブアプリケーション」
4. 承認済みのリダイレクト URI：
   ```
   https://{cognito-domain}.auth.{region}.amazoncognito.com/oauth2/idpresponse
   ```
5. クライアント ID とクライアントシークレットをメモ

**Cognito 側:**

1. 「ID プロバイダーを追加」
2. 「Google」を選択
3. Google のクライアント ID とクライアントシークレットを入力
4. 承認されたスコープ：`openid profile`
5. 属性マッピング：
   | Google 属性 | Cognito 属性 |
   |------------|-------------|
   | name | name |
   | sub | username |

#### Step 4: ホストされた UI（コールバック URL）の設定

1. アプリクライアント → 「ホストされた UI」
2. 許可されているコールバック URL：
   ```
   http://localhost:5173/auth/google/callback
   ```
3. OAuth 2.0 付与タイプ：「認証コード付与」
4. OpenID Connect スコープ：`openid`, `profile`

#### 設定完了後の確認情報

以下の情報をアプリケーション設定に使用：

```properties
# application.properties
aws.region=ap-northeast-1
aws.cognito.user-pool-id=ap-northeast-1_xxxxxxxx
aws.cognito.client-id=xxxxxxxxxxxxxxxxxxxxxxxxxx
aws.cognito.domain=ap-northeast-xxxxxxxx
aws.cognito.redirect-uri=http://localhost:5173/auth/google/callback
```

## トークンをどこに保存するか

### 選択肢の比較

| 保存場所            | XSS耐性 | CSRF耐性 | 実装の容易さ |
| ------------------- | ------- | -------- | ------------ |
| localStorage        | 脆弱    | 安全     | 簡単         |
| sessionStorage      | 脆弱    | 安全     | 簡単         |
| Cookie (通常)       | 脆弱    | 脆弱     | 簡単         |
| **HttpOnly Cookie** | 安全    | 対策必要 | やや複雑     |

### HttpOnly Cookieを選んだ理由

#### XSS攻撃への耐性

```javascript
// localStorageの場合 - XSSで盗まれる可能性
const token = localStorage.getItem("access_token");
// 悪意のあるスクリプトが実行されると、トークンが盗まれる

// httpOnly Cookieの場合 - JavaScriptからアクセス不可
document.cookie; // httpOnly Cookieは表示されない
```

`httpOnly` 属性により、JavaScript から Cookie にアクセスできなくなり、XSS攻撃でトークンを盗まれるリスクがなくなります。

## 認証フローの設計

ログイン、トークンリフレッシュ、ログアウトは以下のようなフローになります。

### ID/パスワードでのログイン

```
[ユーザー] → POST /auth/login (userId, password)
                    ↓
            [バックエンド] → [Cognito] 認証リクエスト
                    ↓
            トークン発行（Access, Refresh）
                    ↓
            Set-Cookie で httpOnly Cookie に保存
                    ↓
[ユーザー] ← レスポンス (userId, userName)
```

### Google SSO でのログイン

```
[ユーザー] → GET /auth/login/google/url
                    ↓
            認証URLを生成（state含む）
                    ↓
[ユーザー] ← リダイレクトURL
         ↓
[Google] ← ログイン画面
         ↓
[ユーザー] ← コールバック（code, state）
         ↓
[ユーザー] → POST /auth/login/google?code=xxx&state=yyy
                    ↓
            [バックエンド]
              1. state検証（CSRF対策）
              2. code → token 交換（Cognito経由）
              3. ユーザー情報取得
              4. DBに登録（新規の場合）
                    ↓
            Set-Cookie で httpOnly Cookie に保存
                    ↓
[ユーザー] ← レスポンス (userId, userName)
```

stateパラメータは認証リクエスト毎にランダムに生成され、コールバック時に検証します。
こうすることによって、CSRF対策になります。

### トークンリフレッシュ

```
[ユーザー] → POST /auth/refresh
            （refresh_token Cookie が自動送信）
                    ↓
            [バックエンド] → [Cognito] リフレッシュ
                    ↓
            新しい Access Token を発行
                    ↓
            Set-Cookie で更新
                    ↓
[ユーザー] ← レスポンス
```

### ログアウト

```
[ユーザー] → POST /auth/logout
            （access_token Cookie が自動送信）
                    ↓
            [バックエンド]
              1. Cognito GlobalSignOut 実行
              2. 全ての認証 Cookie を削除
                    ↓
[ユーザー] ← レスポンス
```

## Spring Security の実装

以下のようなクラスを作成し、設定しています。

```java
@Configuration
@EnableWebSecurity
@RequiredArgsConstructor
public class SecurityConfig {

  // 1. カスタムコンポーネントの DI
  private final CognitoTokenValidationFilter cognitoTokenValidationFilter;
  private final CookieBearerTokenResolver cookieBearerTokenResolver;

  @Bean
  SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    // 2. CORS 設定
    http.cors(withDefaults());

    // 3. CSRF 無効化（REST API + Cookie SameSite で対策済み）
    http.csrf(csrf -> csrf.disable());

    // 4. 認可ルール + OAuth2 Resource Server 設定
    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**").permitAll()      // 認証エンドポイント
            .anyRequest().authenticated())                     // その他は認証必須
        .oauth2ResourceServer(oauth2 -> oauth2
            .bearerTokenResolver(cookieBearerTokenResolver)   // Cookie からトークン取得
            .jwt(withDefaults()))                              // JWT 検証（自動設定）
        .addFilterAfter(cognitoTokenValidationFilter,         // Cognito 追加検証
            BearerTokenAuthenticationFilter.class);

    return http.build();
  }

  // 省略

}
```

### JWT 署名検証

`application.properties` に issuer-uri を設定すると、Spring Security が自動で JWK Set を取得して署名検証を行います。

```properties
# application.properties
spring.security.oauth2.resourceserver.jwt.issuer-uri=https://cognito-idp.ap-northeast-1.amazonaws.com/ap-northeast-1_xxxxx
```

#### JWK Set とは

**JWK Set（JSON Web Key Set）** は、JWT の署名を検証するための**公開鍵の集合**を JSON 形式で表現したものです。

### CookieBearerTokenResolver

Spring Security では `Authorization: Bearer <token>` ヘッダーからトークンを取得しています。このシステムではHttpOnly Cookie を使うため、Cookie から取得するようにしています。

### CognitoTokenValidationFilter

JWT の署名検証だけでは**ログアウト後のトークンを拒否できない**ため、Cognito の `GetUser` API でトークンが本当に有効かを確認しています。
